# 工程分层与模块边界

本框架按可扩展的应用工程组织：通信、平台适配、应用流程、状态、页面和视图具有独立职责。Linux 示例同时给出这些模块的实际连接方式，后续产品可以沿用结构，替换自己的协议、业务模型和界面。

本文说明工程结构和接口边界。它是后续逐层学习的依据，不表示框架课程已经全部完成。

## 1. 框架和产品分别提供什么

框架提供可复用机制：字节缓冲、消息通道、协议调用、非阻塞传输适配、GUI 消息调度、导航和显示端口。

产品提供具体含义：报文格式、命令、业务状态、操作流程、页面、布局、资源和硬件初始化。本仓库中的 `examples/linux/` 是一个结构完整的示范应用；其中的温度查询和协议只属于案例。

| 位置 | 职责 | 允许了解的内容 |
| --- | --- | --- |
| `communication/` | 缓冲、队列、通道和 `comm_link` | 内存消息、编解码回调、传输回调 |
| `ports/linux/` | pthread、fd 和 Linux 显示适配 | 操作系统 API、LVGL 显示接口 |
| `src/navigation.c` | 页面注册、导航、生命周期和事件分发 | 通用页面与事件接口 |
| `src/gui_worker.c` | 从 RX 通道取消息，在 GUI 线程调用项目处理函数 | 通道、回调、每轮处理预算 |
| 产品的 `protocol/` | 线路编码、解码和项目消息转换 | 产品命令、字段、字节布局 |
| 产品的 `domain/` | 保存业务状态及其更新规则 | 产品数据及纯 C 类型 |
| 产品的 `application/` | 解释消息、执行用户意图、调用服务、更新模型 | 产品协议接口、模型、服务 |
| 产品的 `presentation/pages/` | 页面生命周期、交互、读取模型和刷新视图 | 导航、模型、视图、注入的应用回调 |
| 产品的 `presentation/views/` | 控件、布局、样式和显示内容 | LVGL、传入的显示数据与交互回调 |
| 产品的 `platform/` | 打开连接、绑定适配器、推进连接和释放资源 | 具体平台和注入的协议接口 |
| 案例的 `simulation/` | 解释模拟设备收到的命令，生成设备回复 | 案例协议和模拟设备状态 |
| 产品的 `app/` | 初始化、模块连接、主循环和退出顺序 | 各模块公开接口 |

模块可以调用其他模块的公开接口，但不要通过包含其私有 `.c` 文件或访问内部对象来建立依赖。

## 3. 依赖方向

下面的箭头表示“使用另一个模块的公开接口”，不表示另建一个线程。

```text
main
  └─ app：创建对象，注入回调和通道，安排生命周期
      ├─ application / worker
      │   ├─ domain / model
      │   ├─ protocol
      │   ├─ application / service
      │   └─ lak_gui_worker
      ├─ presentation / pages
      │   ├─ domain / model
      │   ├─ presentation / views
      │   └─ lak_navigation
      ├─ protocol：由 app 注入连接
      ├─ platform / connection
      │   ├─ lak_comm
      │   └─ lak_linux
      ├─ simulation / device
      │   └─ protocol
      └─ lak_display_linux
```

应用 worker 通过组装入口注入的通知回调告知页面“状态已更新”，无需包含某个具体页面的头文件。页面通过注入的操作回调表达“查询温度”，无需打开 fd、组织报文或直接访问 TX 队列。

组装入口把案例协议传给连接模块；连接模块只通过通用协议接口调用它，不包含案例协议头文件。模拟设备独立消费设备端 RX、解释查询并把回复放入设备端 TX，平台模块无需判断温度命令。

模型不引用页面、LVGL 或通信模块。视图不引用模型、导航或通信模块。这样协议变化时不必修改控件，布局变化时不必修改通信调度，页面销毁也不会销毁设备状态。

## 4. 两个 worker 的职责

`lak_gui_worker` 和 `demo_gui_worker` 分别处于框架和应用中。

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `lak_gui_worker` | 定时从通道取消息，以零等待方式调用处理函数，限制每轮消息数量 | 识别温度、保存产品状态、决定导航、创建控件 |
| `demo_gui_worker` | 解释案例消息，更新模型，处理查询意图，通知表现层 | 读写 socket、维护字节缓冲、布局控件 |

框架 worker 只调用项目注入的函数。项目函数内部的编码规则和业务行为仍由项目定义；“由框架调用”不代表“应写进框架实现”。

新应用使用 `lak_gui_worker` 建立应用消息入口。它不依赖导航器，不要求任何页面已经存在。

旧的 `lak_comm_bridge` 接口仍然保留，提供“RX 消息直接转为导航事件”的兼容路径。该桥接器在没有当前页面时暂停消费，适合原有接入方式。不要让旧桥接器与新 worker 同时消费同一个 RX 通道，否则它们会竞争取走消息。

## 5. 从按钮到设备，再回到界面

用户点击查询按钮后的发送流程：

```text
view 接收按钮事件
  → page 将其转为查询意图
  → app 注入的操作回调
  → application worker
  → service 构造项目查询消息并投递 TX 通道
  → comm_link 调用项目编码器
  → fd 传输适配器写出字节
```

设备消息进入应用后的接收流程：

```text
fd 传输适配器读入字节
  → comm_link 管理流缓冲并调用项目解码器
  → 完整消息进入 RX 通道
  → lak_gui_worker 在 GUI 线程调用应用 worker
  → 应用 worker 提取温度，更新 model
  → app 注入的通知回调
  → page 读取 model，要求 view 更新显示
```

两条流程的边界明确：

- `service` 投递成功，只代表本地队列接受请求，不能证明设备执行成功。
- `protocol` 定义消息如何表达，包括线路分隔、字段和内存消息转换。
- `comm_link` 调用编码器与解码器，处理部分读写、缓冲和通道背压。
- `worker` 决定消息怎样改变应用状态。
- `page` 决定这个状态在当前页面怎样显示。

## 6. 模型与页面分离

`demo_model` 的生命周期覆盖整个应用，保存界面需要的温度、请求进行状态和错误状态。这里的持久状态指跨页面保留，尚未实现重启后的文件或设备存储。页面只借用模型，并在创建或恢复显示时读取当前值。

假设首页显示温度，用户进入设置页之后收到新温度：

1. 应用 worker 仍然消费消息并更新模型。
2. 当前页面只处理与自己有关的显示更新。
3. 用户返回首页时，首页重新读取模型，显示最新温度。

同样，首个页面尚未创建时也能接收消息并更新模型。设备状态不依赖当前是否存在显示它的控件。

不要让每个页面分别解析同一类设备报文，也不要把页面标签里的文本作为全局业务状态。字段校验与业务含义在协议或应用层完成，显示格式在表现层完成。

## 7. 线程和调度

示例只使用一个主线程：

```text
主循环
  ├─ 推进本地连接两端的非阻塞收发
  ├─ 模拟设备消费命令，并将回复投递到设备 TX
  ├─ 执行 LVGL 定时器
  │   ├─ GUI worker 消费 RX 消息
  │   └─ 导航处理待执行的页面切换
  └─ 短暂休眠
```

`worker` 是模块名称，不代表创建了后台线程。使用 pthread 队列也不代表框架自动创建了线程。

示例中的模型、worker、page、view、导航和 LVGL 都在同一个 GUI 线程执行。`lak_gui_worker` 的所有接口也必须由 GUI 线程调用，其回调应尽快返回，不应执行阻塞读写或耗时工作。

真实项目可以另建通信任务，让它独占 `comm_link`、传输对象和流缓冲，通过线程安全 TX/RX 通道与 GUI 线程交接。通信任务不得直接操作 LVGL 或并发修改本示例的模型；跨线程能力来自明确的数据交接，而不是目录分层本身。

当前温度查询限制同一时间只有一个待回复请求，应用 worker 在等待达到 2 秒时将请求标记为失败。这是案例应用策略；框架不预设超时、重试、请求编号或事务匹配方式。

## 8. 生命周期与所有权

组装入口负责将模块按依赖关系初始化，并在退出时按相反方向停止和释放。

| 对象 | 所有者 | 有效期与约束 |
| --- | --- | --- |
| 模型、模拟设备状态和应用上下文 | `demo_app` | worker、page 或模拟设备调度仍可能访问时必须有效 |
| socket、link、队列、传输对象 | `demo_connection` | 停止消费者与生产者后才能释放 |
| GUI 接收定时器 | `lak_gui_worker` | 反初始化时删除；它不关闭或销毁 RX 通道 |
| 页面根屏幕 | `lak_navigation` | 由导航器创建、切换和销毁 |
| 子控件和视图句柄 | 页面与视图 | 跟随页面生命周期，不得保留已销毁控件指针 |
| 回调收到的 `comm_frame_t` | 当前消息处理调用 | 仅本次回调有效，需要保存的字段必须复制到模型或其他自有存储 |
| 页面事件中的借用数据 | 当前事件分发调用 | 需要延后处理时必须复制 |

新应用应遵守以下顺序：

1. 初始化 LVGL 和显示端口。
2. 创建模型、连接和服务，准备应用回调上下文。
3. 初始化导航和应用 worker；页面可以稍后再打开。
4. 启动主循环，推进连接、模拟设备、GUI 定时器与导航。
5. 收到退出请求后，由主循环停止工作，停止 GUI worker 和消息生产者，再释放队列、连接、页面、显示和 LVGL。

实际存在通信线程时，销毁队列前必须停止并等待相关线程退出。不能在回调尚未返回时销毁正在执行的 worker，也不能在普通控件事件回调中直接拆除整个应用。

## 9. 构建目标也表达模块边界

框架目标：

| 目标 | 内容 |
| --- | --- |
| `lak_comm` | 操作系统无关的通信核心 |
| `lak_linux` | pthread 通道和 fd 传输适配 |
| `lak_navigation` | 页面导航与事件分发 |
| `lak_gui_worker` | GUI 线程的通用消息调度 |
| `lak_gui` | 保留原有 GUI 接入入口，聚合 GUI 能力并保留旧桥接 |
| `lak_display_linux` | SDL、FBDEV、HEADLESS 显示适配 |

示例目标按职责拆成 `demo_model`、`demo_protocol`、`demo_service`、`demo_worker`、`demo_views`、`demo_pages`、`demo_connection`、`demo_device` 和 `demo_app`；`lak_demo` 是最终可执行程序。

顶层 `CMakeLists.txt` 负责选择配置和装配模块。通信、通用 GUI、Linux 端口和各示例目录分别维护自己的 `CMakeLists.txt`。

使用目标的 `PUBLIC`、`PRIVATE` 依赖和包含路径，可以让“哪些模块能看到哪些接口”在编译中体现出来。增加页面时应扩展表现层目标，而不是把页面源码加入 `lak_comm` 或把整个工程的头文件路径全部设为全局可见。

## 10. 常见改动应该落在哪一层

| 需求 | 首先修改的位置 |
| --- | --- |
| 换行符协议改成帧头、长度和 CRC | 产品 `protocol/` |
| 收到查询后回复其他业务数据 | 产品应用处理或案例的 `simulation/` 设备业务实现 |
| 增加温度告警状态和规则 | 产品 `domain/` 与 `application/` |
| 点击按钮改为查询另一个设备参数 | 页面意图回调及应用服务 |
| 调整字体、颜色、布局或使用界面生成工具 | `presentation/views/` |
| 新增页面、进入时刷新、返回时恢复状态 | `presentation/pages/` |
| 将 socket 换成配置好的串口 | 产品 `platform/`，复用 fd 端口 |
| 改变读取预算、短写处理或通用队列机制 | 确认是通用问题后修改框架通信模块 |
| 更换板级显示驱动 | 项目平台适配或新的通用显示端口 |

如果采用 `gui_guider` 等生成工具，可以把其控件创建和布局代码放在 views 一侧，将页面生命周期、消息解释和业务操作放在手写模块。生成代码更新时，应用状态和流程不应随之被覆盖。

## 11. 后续学习顺序

1. 从 `main.c` 和 `app/demo_app.c` 认识组装入口、主循环和资源关系。
2. 阅读 `domain/demo_model.*`，区分持久业务状态和页面临时状态。
3. 沿 `views → pages → worker → service` 追踪一次用户查询。
4. 阅读 `protocol`、`platform` 和 `comm_link`，追踪消息与字节的转换，再看 `simulation` 如何独立处理设备端查询。
5. 沿 `RX → lak_gui_worker → application worker → model → page → view` 追踪一次回复。
6. 运行 `--tour`，观察无页面时接收、非首页时更新、返回首页读取最新模型。
7. 再学习导航生命周期、历史栈、事件分发和退出清理。

每一步都结合实际源码与运行结果学习，后续再单独整理复习题和新人学习笔记。
